# Rebuild3D v2 差异分析与实施计划

日期：2026-10-08。状态：方案评审，尚未实施本计划。

依据：[v2 启动文档](Rebuild3D-项目启动文档-v2.md)、[v1 启动文档及实施记录](Rebuild3D-项目启动文档.md)、[现有验收记录](验收记录-2026-10-08.md)，以及当前仓库代码。

本轮只新增此计划，保留 v1、v2 原文，不修改应用实现。下文“已验证”引用既有验收记录与日志，不表示本轮重新运行了测试。

## 1. 判断与实施范围

**v2 合理，适合在现有工程上增量实现。** SwiftUI、RealityKit / Object Capture、本地重建、带贴图 USDZ、自包含项目、P0 → P1 → P2 的基本方向均未变化。主要变化是把“普通 iPhone 照片可直接使用”落实为输入、交互、持久化和验收要求。

当前已有可用的重建与项目管理基础。接下来应优先补齐真实 HEIC 路径和导入层，随后完成普通用户的操作闭环。P1 的坐标与投影探针可以早做，完整视角界面在 P0 验收后接入。

首版交付分开记录两个里程碑：

- **P0**：普通 HEIC / JPEG → 带贴图模型 → 查看、保存、重开、导出；包括 iPhone 16 Pro 原始 HEIC 的真实验收。
- **P1**：同一重建结果中的照片与机位关联、照片视角、并排对比、持久恢复。

DNG、任意视频抽帧、系统照片图库、手机自动传输、通用研究数据解析器、其他模型格式继续留在 P2。文档、代码注释和 README 的语言约定沿用现有规则：`doc/` 内可用中文，代码注释和 README 等使用英文。

## 2. v1 → v2 的主要差异及现有实现缺口

| 主题 | v1 | v2 | 当前实现与后续动作 |
| --- | --- | --- | --- |
| 普通照片入口 | 提到系统相机，格式要求较笼统 | 常见 iPhone HEIC、JPEG 是 P0，不要求手动转换或扫描应用 | 已列入 HEIC 扩展名，尚无真实 HEIC 闭环验收；需验证解码、方向、颜色与实际重建 |
| 支持边界 | 没有细分 iPhone 拍摄格式 | ProRAW / DNG 为 P2；Live Photo 取静态图，伴随视频忽略 | 现在不支持的输入均进入同类错误；需区分不支持的照片、无法读取、重复、忽略的辅助文件 |
| 研究数据 | 未详细说明照片与研究资料关系 | 只需照片；不混合 `rgb/` 与 `rgb_keyframe/`，无须轨迹和深度 | 当前已不依赖外部资料，且文件夹导入不递归；保留此行为，补充摘要和相关测试 |
| 导入判断 | 普通图片导入 | 文件类型结合实际解码，EXIF 可缺失，逐张处理 | 当前先按扩展名筛选，要求图像数量等于 1，并固定读取索引 0；需改进内容识别及 HEIF 主图选择 |
| 身份与重复 | 稳定照片 ID 主要服务项目和位姿 | 明确同名不覆盖、重复可解释，工作副本可追溯 | UUID 命名已避免覆盖；去重只覆盖同一次调用中的相同 URL，跨批次或重开后重复仍会加入 |
| 原图与工作副本 | 保留原图，缩放需关联参数 | 原图字节保留；按需转换；方向、尺寸、裁剪、颜色处理关系可持久恢复 | 已复制保留原图；只存尺寸和方向，缺少处理配方、转换关系与重建输入快照 |
| 界面与默认设置 | 先新建项目，再导入、选择质量 | 突出添加照片与开始重建，设置折叠，诊断信息隐藏 | 当前首次导入前必须选项目保存位置，质量选项默认展开；需改造入口和状态展示 |
| 错误与进度 | 可理解的进度和错误 | 不伪造百分比，不根据通用失败码猜测模糊/覆盖问题；可定位到受影响照片 | 引擎进度来自真实事件，但准备阶段仍展示初始百分比，内部阶段名及样本 ID 会进入主界面 |
| 项目格式 | 自包含目录或文档包 | 优先文档包，增加导入/转换记录，清缓存不破坏视角 | `.rebuild3d` 文档包及系统注册已具备；需扩展元数据、兼容旧格式和保护多文件提交一致性 |
| 测试与完成标准 | 普通对象闭环，实拍验证要求较宽泛 | 59 张 HEIC、33 张 JPG 基线；iPhone 16 Pro 实拍为必要验收 | 目前真实成功证据是 155 张 1080×1080 JPEG；不能据此认定高分辨率 HEIC 或 v2 已通过 |
| P1 | 获取机位、内参、构图与持久化 | 强化普通照片及工作副本条件下的映射 | 已有独立 `.poses` 探针；完整视角功能和投影正确性仍待实现 |

代码核查入口：

- [PhotoImporter.swift](../Sources/Rebuild3DCore/PhotoImporter.swift)：类型筛选、索引 0、批次内 URL 去重、导入问题结构。
- [Project.swift](../Sources/Rebuild3DCore/Project.swift)：照片字段、格式版本 1、模型与照片的关系。
- [ProjectStore.swift](../Sources/Rebuild3DCore/ProjectStore.swift)：仅接受当前版本，原子保存、不可变模型提交及路径检查。
- [ReconstructionEngine.swift](../Sources/Rebuild3DCore/ReconstructionEngine.swift)：临时输入目录、单模型请求、原始样本事件与进度。
- [AppModel.swift](../Sources/Rebuild3DApp/AppModel.swift)、[ContentView.swift](../Sources/Rebuild3DApp/ContentView.swift)：先建项目的限制、默认展开设置、导入提示与空状态。

## 3. 可以保留的基础与证据边界

以下工作已有实现，无需重复搭建：

- Swift Package 原生应用、诊断 CLI、应用打包脚本、上游来源与许可证保留。
- 自包含项目、UUID 照片名、原图复制、相对路径、安全路径校验、可重建缩略图。
- 单任务重建、真实进度事件、取消、持续监听至会话结束。
- 新模型写入完成后切换项目引用；失败或取消保留旧模型。
- RealityKit 彩色模型查看、旋转/缩放/平移、完整 USDZ 导出。

既有证据：13 项自动化测试通过；155 张 JPEG 已完成真实重建、应用内查看、保存重开、导出和独立 SceneKit 渲染。独立位姿探针关联了 155 张输入，其中 147 张有位姿及内参/畸变数据，没有 URL 匹配失败。

这些证据有明确边界：测试图片分辨率较低，HEIC、iPhone 16 Pro 实拍、完整导入到导出的 UI 序列、P1 投影仍未验收。位姿探针成功不等于相机坐标或构图正确。Quick Look 验收尚未通过。当前无需把既有 JPEG 基础推倒重做，也不能把它记作 v2 的完整验收。

## 4. 实施前应统一的约定

### 4.1 需求版本和实际进度分开记录

v2 开头“尚未完成本项目开发或实际重建效果验证”与仓库实际状态不一致；v2 也没有收录 v1 末尾的实施记录。

建议实施时更新为：已有 P0 基础实现和公开 JPEG 验证，v2 的 HEIC、实拍及交互验收待完成。v1 保留历史；v2 作为需求依据；验收记录继续保存实际证据。修改需求文档时不抹去未通过项。

### 4.2 添加照片时自动建立可恢复草稿

v2 第 4 节仍写先新建项目，第 6 节要求空状态只突出添加照片。建议统一为：

1. 启动后直接添加或拖入照片，应用在 Application Support 的受管理目录建立草稿项目。
2. 导入的原图和清单及时落盘；草稿可在重新启动后恢复，不依赖会被清理的临时目录。
3. 用户执行保存时再选 `.rebuild3d` 的名称和位置。复制/迁移成功并校验可打开后，才切换项目引用和清理原草稿。
4. 用户明确丢弃时才删除相应草稿；保存失败或空间不足时保留可恢复数据。
5. 工具栏保留新建、打开；这两项不是首次添加照片的前置条件。

这是本计划的产品建议，v2 尚未明确草稿生命周期。工作量包括退出恢复和保存失败处理，不能只替换空状态按钮文字。

### 4.3 HEIC 支持按实际内容验证

“ImageIO 可解码”“引擎可以使用”“能够生成合格模型”应分开验收。当前 `CGImageSourceGetCount == 1` 的限制是待验证的兼容风险，不能据此断言所有 HEIC 都有问题。

实现应识别实际类型，并对 HEIF 使用明确的主图规则；不能把所有多图容器都视为普通动画，也不能默认索引 0 就是目标图。Apple 提供 [CGImageSourceGetPrimaryImageIndex](https://developer.apple.com/documentation/imageio/cgimagesourcegetprimaryimageindex%28_%3A%29) 获取 HEIF 主图索引。主图选择规则要同时用于元数据、缩略图和原图预览，并与重建实际使用的图像核对。

JPEG/HEIC 是必要支持。PNG 单独验证后声明兼容；现有 TIFF 支持作为兼容项保留核查，不扩大为 v2 必须支持所有图像格式的承诺。DNG 即便 ImageIO 能解码，也应按明确的 P2 产品规则处理。

### 4.4 原图优先，工作副本按证据启用

建议首轮以原图直入引擎为基线，保持逐字节复制。只有真实兼容性、方向或资源测试显示需要时，才引入相应转换。

- 照片记录包含实际类型、主图索引、原始像素尺寸、EXIF 方向及可读取的必要拍摄/颜色信息；元数据缺失使用明确的未知状态。
- 用原文件内容摘要辅助跨批次、跨重开的精确去重；不同内容的同名照片均保留，不在 P0 做视觉近似去重。
- 工作版本记录来源照片 ID、处理版本、输入/输出尺寸、方向变换、缩放、裁剪、颜色处理与文件摘要。
- 区分文件编码像素坐标、方向校正后的显示坐标、实际送入引擎的坐标。原文件未转换时，文件像素映射可为恒等；显示方向仍单独记录。
- 引擎内部自动降采样另行记录。不能未经验证就把返回内参认定为原图分辨率对应的参数。

颜色方面，建议 P0 先验证受颜色管理的 SDR 预览与模型对照，完整保留原图的宽色域/HDR 信息；如需生成 SDR 工作副本，显式记录色彩转换或色调映射。v2 没有要求首版实现完整 HDR 材质与显示链路。不能把“统一颜色处理”直接解释为把所有原图转成普通 JPEG。

### 4.5 简化文件结构，同时保证结果一致

v2 的 `imports.json` 是拟议结构。建议 P0 先扩展现有 `project.json` 保存照片身份和导入属性，避免两份可编辑清单互相矛盾；另保存每次运行的不可变输入快照，关联原图和工作版本。P1 的相机记录绑定同一个运行 ID 和模型版本。

建议结构增量：

```text
project.json                 # 当前照片、设置、已提交结果引用和格式版本
images/                      # 原图
runs/<run-id>/inputs.json     # 本次重建的照片/工作版本/转换快照
runs/<run-id>/cameras.json    # P1：同一次重建的相机结果与状态
models/<model-id>.usdz        # 不可变模型
cache/                       # 可再生成的工作图和其他中间文件
```

先写入并校验不可变资料，再原子切换 `project.json` 的引用。对多个 JSON 分别执行原子写入，并不自动构成整个项目的事务。缓存清理后，运行快照、相机、原图和模型必须仍可恢复。

项目格式随实际字段变化升级，独立于需求文档的“v2”名称。读取现有格式 1 项目时保留原 ID 和模型，缺失属性标记未知或从原图补读；迁移写入失败时保留原项目可用，不要求重新重建，也不伪造旧结果的相机记录。

### 4.6 提前验证两项引擎接口风险

第一项是无效/跳过样本的逐张关联。当前模型请求只提供样本 ID 事件，没有保存 ID 与原图的可靠对应。先验证文件夹输入配合 `.poses` 返回的 [urlsBySample](https://developer.apple.com/documentation/realitykit/photogrammetrysession/poses/urlsbysample) 能否覆盖相关事件；不能覆盖时，评估维护自定义样本 ID 的输入方式，并检查原有元数据是否仍可利用。没有证据的映射不能用文件排序代替；无法关联时只显示有依据的批次提示和诊断，不错误标记某张照片。

第二项是 P1 投影能力。现有查看器的普通透视相机不能仅靠机位和固定视场角还原照片。Apple 对 [ProjectiveTransformCameraComponent](https://developer.apple.com/documentation/realitykit/projectivetransformcameracomponent) 的文档约定为对称透视或正交投影，因此不能未经试验就认定它支持任意偏心主点。需验证适用于当前查看器的投影/画面重映射路径；若只能近似，应明确标记并记录偏差。

## 5. 建议实施顺序与每步完成条件

### S0：对齐基线，先验证高风险输入

**目的：在重构导入或界面之前，确定普通 HEIC 是否需要工作副本，以及真实资源压力。**

工作：

- 更新进度索引，保留既有 JPEG 与取消/失败证据；核实样例目录、来源、数量、尺寸、方向、颜色和格式。
- 59 张 HEIC、33 张 JPG 分别仅用照片建立导入→重建→导出基线；TMO 仅选择 `rgb/`。
- 记录每组实际格式、配置、日志、输出、耗时与内存统计口径；检查 USDZ 网格、UV、材质与内嵌贴图，并独立渲染。
- 用真实 iPhone 16 Pro HEIC 尽早验证读取与引擎入口；若已有合格拍摄组，同阶段直接做完整重建。
- 验证主图、方向、颜色与样本 ID 关联风险；延续已有位姿探针做小范围坐标核查。

完成条件：至少一组 HEIC 和一组 JPEG 的真实路径有明确结果；遇到 HEIC 失败，记录具体失败层并只做打通该层所需的修正。没有成功完成前不把 HEIC 兼容记为通过。

涉及：现有 CLI、探针、验收记录；必要时最小修改 `PhotoImporter`。不重新建立仓库或重写重建引擎。

### S1：扩展数据结构与可靠保存

**依赖 S0 的实际输入结论；先固定数据关系，再完善导入和界面。**

工作：扩展照片元数据及内容摘要；定义工作版本和运行快照；实现旧项目读取/迁移；为模型与将来的相机结果建立同一运行的引用；实现原子提交及失败恢复。仅为经 S0 证实需要的转换实现处理器。

完成条件：旧项目无需重建即可打开；新项目保存、移动、重开和删除缓存后仍恢复原图/模型/转换记录；迁移或提交失败不替换既有成功结果。

涉及：`Project.swift`、`ProjectStore.swift`；建议新增 `PhotoPreparation.swift` 承担工作副本生成和变换记录。

### S2：补齐照片导入与逐张结果

工作：

- 文件类型与实际内容共同判断；统一主图、方向与颜色处理规则，后台逐张处理，避免批量原图常驻内存。
- 提供结构化结果：已导入、重复、不支持的照片、无法读取、已忽略。视频、辅助文件、隐藏文件与子目录按明确规则汇总，保留非递归行为。
- 跨导入、跨重开精确去重；同名不同内容不覆盖；缺少 EXIF 不单独构成拒绝理由。
- 保留原始文件名和稳定 ID。不可读文件使用带文件名的占位行，不要求生成不存在的缩略图。
- 持久化运行输入对应关系，按 S0 验证的策略关联引擎样本问题。用户看见可执行说明，内部错误细节进入诊断。

完成条件：混合 HEIC/JPEG/DNG/MOV/辅助文件/损坏文件时，所有可用照片仍可导入，分类与计数准确；重排不改变 ID，移除不破坏旧模型使用的原图；局部问题不会使整个批次失败。

涉及：`PhotoImporter.swift`、`PhotoPreparation.swift`、`ReconstructionEngine.swift` 的事件结构及相关测试。

### S3：落实添加照片即可开始的界面

工作：

- 落实可恢复草稿，支持首次启动直接添加或拖入照片；保存时选择正式位置。
- 导入后突出开始重建；默认使用经样例验证的推荐配置。质量与背景隔离放入可展开选项，用户标签使用可理解的名称。
- 区分准备、重建、保存、完成、取消和失败。只有引擎提供可靠进度时显示百分比，其余使用活动指示。
- 展示导入摘要和逐张问题，诊断可展开；失败解释发生了什么、是否可重试，不推测未经检测的原因。
- 保留当前模型查看、导出和已保存结果恢复能力。

完成条件：首次启动无需先选择项目路径或质量即可添加照片并重建；退出可恢复草稿；保存失败保留数据；修改输入或配置后能识别当前模型已过期。

涉及：`AppModel.swift`、`ContentView.swift`、应用生命周期；建议新增 `DraftProjectStore.swift` 集中管理草稿。

### S4：完成 v2 的 P0 实拍与可靠性验收

工作：用最终应用而非只有 CLI 完成完整流程，执行下节测试矩阵。iPhone 16 Pro 系统相机 HEIC 原文件必须参与完整闭环；再验证普通 JPEG 无辅助文件路径。

资源验证包含实际常用分辨率。Apple 说明普通 HEIF 可达 24MP、HEIF Max 可达 48MP，因此不能只用 12MP 公共照片推断设备表现；建议加入 24MP 实拍，并将 48MP 作为额外压力样本，具体以输入文件为准。[Apple 格式与分辨率说明](https://support.apple.com/en-us/119916)

完成条件：P0 必要项均通过，或明确记录尚未通过的项；没有 iPhone 16 Pro HEIC 实拍成功证据时，P0 不标记全部完成。记录内存时区分应用进程采样、系统压力和可观察的辅助进程，不把当前 RSS 当作系统总峰值。

涉及：`Tests/`、验证脚本、UI 操作记录和真实模型检查；更新验收文档。

### S5：完成 P1 照片视角与对比

**完整功能依赖 S4；S0 的小范围技术验证不受此限制。**

工作：
